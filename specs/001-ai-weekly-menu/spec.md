# Feature Specification: 生成AIで1週間の夜の献立計画

**Feature Branch**: `[001-ai-weekly-menu]`  
**Created**: 2025-10-21  
**Status**: Draft  
**Input**: ユーザー説明: "生成AIを使って、一週間の夜の献立を計画してくれるWebアプリを作りたい。"

## ユーザーストーリー & テスト（必須）

### P1: 「購入した材料」フリーテキスト入力からの週次（夜のみ）献立生成

- 概要: ユーザーが購入済みの材料をフリーテキストで入力すると（例:「鶏もも500g、玉ねぎ2個、豆腐1丁、キャベツ半玉、卵6個、トマト缶1」）、それらを優先的に活用した7日×夜（7スロット）の献立を自動生成し、カレンダー形式で閲覧できる。和洋中は混合で提示。
- 独立テスト: 材料テキスト→正規化→7件の献立が生成され、各料理に「使用した主要材料」が紐づく。
- 朝用リザーブ方針: 本システムは夜の献立のみを生成するが、朝の活用を想定し「入力材料を夜だけで使い切らない」ことを原則とする（在庫を0にしない最小余剰を確保）。
- 受け入れ条件:
  1. Given 材料テキスト, When 生成, Then 7スロットのうち80%以上で入力材料が主要食材として使用される（不足分は補完提案を表示）
  2. Given 料理カード, When クリック, Then 材料マッピング（入力材料/追加購入品）が区別表示される
  3. Given 材料テキスト, When 生成, Then 各入力材料の使用量は在庫から「最小余剰量」（例: 卵=1個, 玉ねぎ=1/4個, 調味料=10g 等）を差し引いた範囲内に収まる（在庫が最小余剰量未満の場合は代替案/追加購入の提案を表示）
  4. Given 料理カード/買い物リスト, When 表示, Then 朝用リザーブ対象の食材が明示ラベル（例: 「朝用リザーブ」）で表示される

### P2: 条件指定・好み反映・スロット再生成（夜のみ）

- 概要: 予算/調理時間/カロリー/除外食材/嗜好（和・洋・中の比率）を指定でき、特定スロットのみの再生成や固定（ロック）が可能。
- 独立テスト: 条件変更→生成→条件に合う提案が出る。特定スロットのみ再生成できる。
- 受け入れ条件:
  1. Given 条件A, When 生成, Then 各料理が条件A（例: 調理時間≦20分）を満たす
  2. Given 月曜夜を固定, When 週再生成, Then 月曜夜のみ不変で他が更新
  3. Given 7 日のスロット並び, When 生成, Then 隣接する 2 日で同一の料理カテゴリ（和/洋/中）が連続しない（例: 1日目が和なら2日目は洋または中）。

### P3: 買い物リストとエクスポート（夜のみ）

- 概要: 1週間分の材料を集計し重複統合/カテゴリ分け（野菜・肉・調味料等）。CSV/PDFエクスポートに対応。
- 独立テスト: 生成結果→買い物リスト→カテゴリ別に数量表示→CSVダウンロード可。
- 受け入れ条件:
  1. Given 7献立, When 集計, Then 同一食材が単位換算の上で合算される
  2. Given リスト画面, When CSV出力, Then 行数=食材点数で欠損なし

### エッジケース

- 矛盾する条件（例: 低予算/高タンパク/短時間の同時要求）→ 明確な理由と代替提案を提示
- アレルゲン/除外食材の混入→ 生成時フィルタ＋出力後検証でブロック
- 単位/分量の不一致（g/個/大さじ）→ 標準化して表示
- 同一料理の過度な重複→ バラエティ制約で抑制
- LLM出力の曖昧さ/不適切表現→ 安全プロンプト＋ポスト検証で修正/再生成
- API失敗/タイムアウト→ フォールバック（短縮プラン/キャッシュ）とリトライ
- 入力材料のみでは7日×夜を充足できない→ 不足食材の最小補完リストを提示し、代替案（品数削減/食材置換）も提示
- フリーテキストの曖昧な表現（「少々」「半分くらい」など）→ 標準量に丸めて注記を付与
- 嗜好/除外/在庫制約により同一カテゴリ非連続が満たせない→ 例外理由を明示し、最小回数での連続に抑制（代替案を提示）
- 在庫が少量で最小余剰が確保できない（例: 卵=1個のみ）→ 追加購入の提案/別食材への置換/余剰免除の理由提示のいずれかを提示（優先度は在庫→置換→免除）

## 要件（必須）

### 機能要件

- FR-001: フリーテキストの材料入力をパース・正規化し、週7日×夜（7スロット）の献立を「入力材料優先」で自動生成する
- FR-002: 人数/アレルギー/嗜好/予算/調理時間/カロリーの入力とバリデーション（材料在庫と矛盾しない提案）
- FR-003: スロット単位での再生成・固定（ロック）
- FR-004: 料理詳細（材料・手順・所要時間・概算栄養の提示）。「入力材料から使用」「追加購入が必要」を区別表示
- FR-005: 買い物リストの自動集計（重複統合・カテゴリ分け・単位統一）。不足分は「追加購入リスト」として分離
- FR-006: CSV/PDFエクスポート
- FR-007: プラン保存/読込/共有リンク発行（匿名でも可）
- FR-008: プロンプト/システムメッセージの管理とバージョニング
  - プロファイル: 「用途別プロンプト（例: parsing, plan-generation, shopping-aggregate）」を profiles として定義し、ID（slug）と semver で管理する
  - バージョン固定: 実行時は各機能が使用するプロファイルIDとバージョンを明示的に固定（pin）する
  - 変更履歴: 変更理由・効果を含む CHANGELOG（profilesごと）を保持する
  - ローダ: ライブラリ側に profiles ローダを実装し、検証（schema/存在/互換性）後に供給する
- FR-009: 安全性対策（アレルゲン検査・免責/注意書き表示）
- FR-010: パフォーマンスSLO（暫定）— p95: 生成開始<3s（ストリーミング開始）/ 完了<15s、p99 エラー率<1%。計測/レポートは観測基盤で実装
- FR-011: 監査用ログ（入力条件・生成要約・再生成履歴）
- FR-012: 代替提案/部分生成— LLM失敗/タイムアウト時は（1）固定スロットを保持し未確定スロットを簡易テンプレで暫定提示（2）短縮プロンプトで再試行（3）最小セットの代替案提示。ストリーミングは部分結果を逐次反映
- FR-013: レシピ/栄養データは LLM 完全生成＋後検証（既存DBなし）
- FR-014: LLM API プロバイダはTBD。コスト上限は現時点なしだがトークン効率を重視
- FR-015: 日本向け表示（食材名/単位は g/大さじ/小さじ等）。和洋中は混合がデフォルト
- FR-016: フリーテキスト材料の曖昧表現/俗称の正規化（例:「玉ねぎ半玉」→ 100g 目安）
- FR-017: 朝用リザーブの確保（夜のみ生成）— 入力材料を夜の献立だけで使い切らず、最小余剰量を確保して表示（料理カード/買い物リストにリザーブを明示）。在庫が最小余剰に満たない場合は代替案や追加購入提案を行う。
- FR-018: 料理カテゴリの非連続制約 — 連続する日で同一カテゴリ（和/洋/中）が続かないように計画し、嗜好比率を維持しつつ並び替え/置換で調整する。
- FR-017: 朝用リザーブの確保（夜のみ生成）— 入力材料を夜の献立だけで使い切らず、最小余剰量を確保して表示（料理カード/買い物リストにリザーブを明示）。在庫が最小余剰に満たない場合は代替案や追加購入提案を行う。

### 主要エンティティ

- UserProfile: 人数・嗜好・除外・アレルギー
- Plan: 週次献立（週開始日・タイムゾーン・ロック状態）
- MealSlot: 日付/時間帯（夜固定）/料理参照/メモ
- Recipe: タイトル/概要/材料（IngredientRef[]）/手順/時間/栄養
- IngredientRef: 食材ID/名称/数量/単位
- ShoppingItem: 食材ID/名称/合計数量/単位/カテゴリ

## 成功指標（必須）

- SC-001: 不要トークン抑制（テンプレ最適化/材料先読み正規化/スロット別詳細化）。測定: 平均（プロンプト+出力）トークン/Plan を継続計測し、四半期で改善率を評価
- SC-002: 提案採用率（提案→確定）≥ 70%（測定: 「スロット提案→ユーザー確定」の比率、重複除外）
- SC-003: アレルゲン混入率=0、検出率≥99.9%（テストで担保）
- SC-004: 出力の重複料理比率 ≤ 15%（入力材料の活用率低下を避けつつバラエティ確保）
- SC-005: 継続利用率（Week2留存）≥ 35%（測定: 初回週のプラン確定から7–14日後の再訪/再生成）
- SC-006: 入力材料活用率 ≥ 80%（測定: 品目ベース）

### メモ

- 対象地域/料理基準: 日本向け、和洋中混合で提示
- LLM/データ: 既存レシピDBなし。LLM完全生成＋検証
- コスト: 上限なし（現時点）。無駄なトークンを使わない方針
- 応答時間: 現状SLOなし（段階的表示で体感改善）

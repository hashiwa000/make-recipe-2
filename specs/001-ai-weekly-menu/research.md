# リサーチ: AI 週次献立プランナー

- 方針: TypeScript + Node.js 20（Fastify）+ 共有コアライブラリ
  根拠: CLI と Web API の両立に強いエコシステム、優れた JSON ツール、PDF/CSV 生成が容易、コミュニティが広い。Library-First と CLI 要件に整合。
  代替検討: Python/FastAPI（開発体験は良いが、1ランタイムでの web+CLI+PDF 連携がやや弱い）; Go（高速だがイテレーション速度と LLM SDK 成熟度で不利）。

- 方針: コアのプランナーライブラリ `packages/menu-core` と CLI コントラクト
  根拠: Library-First と CLI Interface の原則を徹底。Web から独立したコントラクトテストが可能。
  代替検討: まず API に実装（憲法違反; 再利用性/テスト容易性が低下）。

- 方針: OpenAI 互換アダプタによる LLM プロバイダ抽象化
  根拠: プロバイダの差し替えを容易化。プロンプト/バージョニングを集中管理。コスト管理と安全フィルタを単純化。
  代替検討: プロバイダを固定（可搬性低下）; 複数プロバイダへ直呼び（必要性の裏付けなく複雑）。

- 方針: Zod によるバリデーション（DTO）、LLM 後のアレルゲン/単位/多様性検証
  根拠: 明示的スキーマ検証。安全性と品質を決定論的に担保。TypeScript 型との統合が容易。
  代替検討: JSON Schema のみ（コントラクト用途は良いがアプリコードでは扱いにくい）; アドホック検証（不具合の温床）。

- 方針: Prisma + SQLite による保存と共有リンク
  根拠: ローカルで簡潔、PostgreSQL への移行も容易。開発体験が良い。
  代替検討: ファイルシステム JSON（並行性に弱い）; 初手から PostgreSQL（運用コストの正当化が未だ難しい）。

- 方針: 食材パースと正規化のパイプライン
  根拠: 事前正規化により LLM トークンを削減し精度向上。単位の正準化とエイリアス対応を支援。
  代替検討: LLM 依存のパースのみ（コスト/ばらつき増; 決定論的テストが困難）。

- 方針: スロット単位の生成とロックモデル
  根拠: P2 要件（スロット単位の再生成/ロック）を満たす。固定スロットの再利用でトークン節約。
  代替検討: プラン全体の再生成のみ（要件不達）; スロット構造を持たないレシピ単位のみ（カレンダー文脈を喪失）。

- 方針: 単位変換テーブルを用いた買い物リスト集計
  根拠: 重複排除と単位の統一を担保。要件のカテゴリ分け（野菜/肉/調味料 等）に対応。
  代替検討: 文字列マージのみ（単位/別名で破綻）; LLM 要約（合計が非決定的）。

- 方針: CSV は `csv-stringify`、PDF は `pdfkit`
  根拠: 実績のあるライブラリ。現段階ではヘッドレスブラウザへの依存を回避。
  代替検討: Puppeteer（強力だが依存が重い）; wkhtmltopdf（外部バイナリ）。

- 方針: LLM 系エンドポイントはストリーミング応答、非 LLM は SLO 設定
  根拠: 体感性能と UX を改善。仕様で未確定の箇所に過度な SLO を課さない。
  代替検討: ブロッキング応答（UX 低下）; 厳格な SLO（時期尚早）。

- 方針: `/contracts/openapi.yaml` による Contract-first API
  根拠: コントラクトテストと API クライアント生成を可能にし、Test-First を支援。
  代替検討: アドホックなエンドポイント（検証が困難で相互運用性が低下）。

- 方針: スコープは夜のみ（7 スロット）
  根拠: 要件簡素化と検証容易性（活用率/多様性/SLO の測定が明確）。
  代替検討: 朝夕 2 スロット（実装/検証コスト増・本段階では優先度低）。
